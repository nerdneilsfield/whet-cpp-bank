# 虚函数的调用开销是多少？为什么比普通函数慢？

## 问题

从底层角度分析：虚函数调用相比普通（非虚）函数调用，存在哪些额外开销？在高性能场景下如何规避？

## 参考答案

### 普通函数调用 vs 虚函数调用

**普通（非虚）函数调用**，编译期确定地址，生成直接跳转：

```asm
call 0x4011a0  ; 直接调用，地址编译期写死
```

**虚函数调用**，需要三步：

```asm
mov rax, [rdi]          ; 1. 从对象头部取 vptr
mov rax, [rax + offset] ; 2. 从 vtable 中取函数指针（函数槽偏移）
call rax                ; 3. 间接跳转（call 目标在运行时才知道）
```

### 开销来源分析

#### 1. 间接内存访问（2 次额外 load）

- 取 vptr：1 次 load（若对象在缓存则约 4 周期；否则 cache miss → 数百周期）
- 取函数指针：再 1 次 load（vtable 是只读段，热路径下通常在 L1/L2）

#### 2. 无法内联（最大开销来源）

直接调用的目标在编译期已知，编译器可以内联，消除调用开销并进一步做常量折叠、死代码消除。间接调用的目标运行时才确定，**编译器无法内联**，因此也失去了内联带来的所有二次优化机会。

对于小而频繁调用的函数（如 `int getValue()`），内联收益可以超过函数体本身的执行时间。

#### 3. 间接分支预测失败

现代 CPU 有间接分支预测器（IBP），能预测 `call rax` 的目标。若调用点只有一个实际分派目标（单态），预测准确率接近 100%，额外开销可低至 1–2 周期。若多态性高（调用点有多个目标交替出现），预测失败率上升，每次失败约 15–20 周期的流水线清空。

#### 4. Retpoline 开销（Spectre 缓解措施后）

2018 年后，内核和编译器为缓解 Spectre v2 引入了 retpoline（用 `ret` 替代间接跳转）。在开启 retpoline 的编译器下，**每次虚函数调用额外增加约 5–10 周期**（具体取决于 CPU 微架构）。

### 实际开销量级

| 场景 | 额外开销估计 |
|------|-------------|
| 热路径，单态，数据在 L1 | 约 3–5 周期（含 IBP） |
| 冷路径，多态，cache miss | 200–400 周期 |
| 开启 retpoline | +5–10 周期/次 |
| 内联带来的优化损失 | 视函数体大小，可能 10–100 倍差距 |

### 规避手段

**1. 去虚化（devirtualization）——编译器自动**

```cpp
void call(Circle& c) {
    c.area();  // Circle 是 final，编译器直接调用 Circle::area，无 vtable 查找
}
```

触发条件：目标类型在编译期可知（局部变量、final 类、内联时常量折叠）。

**2. 模板多态（静态多态）**

```cpp
template<typename T>
void render(T& shape) {
    shape.draw();  // 编译期展开，零虚函数开销
}
```

代价：代码膨胀、编译时间增加、无法存入异构容器。

**3. 接口聚合 / 类型擦除**

将多态逻辑下沉到批处理层，减少每元素的 vtable 查找次数（数据导向设计 DOD）。

**4. final 关键字**

标记 `final` 类/函数，提示编译器可安全去虚化（见 vtable-007）。

### 结论

虚函数的开销**主要不是 vtable 查找本身**（2 次内存 load，热路径微不足道），而是**无法内联**导致的优化机会损失，以及**多态场景下分支预测失败**的流水线停顿。在高频小函数（<5 指令体）且多态性高的热路径上，开销可能高达普通调用的数十倍；大多数实际业务代码中影响可忽略。
