# `std::deque` 的内存布局？为什么两端插入是 O(1)？

### 问题

`std::deque` 的内存布局是怎样的？它既支持下标随机访问，又支持两端 O(1) 插入，是如何做到的？与 `vector` 相比有哪些代价？

## Explanation

### 内存布局：分段连续（Segmented Storage）

`deque` 不是单块连续内存，而是由若干**固定大小的缓冲块（chunk/buffer）**组成，通过一个**中控数组（map）**管理这些块的指针。

```
map（指针数组，可向两端扩展）:
  [nullptr] [nullptr] [chunk*] [chunk*] [chunk*] [nullptr] [nullptr]
                         ↓         ↓         ↓
                      [e0,e1,..] [e8,e9,...] [e16,...]
                      块0（已满） 块1（已满） 块2（部分使用）
```

- **chunk**：固定大小（如 512 字节，或 `sizeof(T)` 决定的若干元素），是连续内存。
- **map**：存各 chunk 指针的动态数组，本身可向两端扩展（类似 vector，但两端都预留空间）。

### 两端插入 O(1) 的机制

**尾部 `push_back`**：
- 当前尾部块仍有空位 → 直接在末尾构造元素，O(1)。
- 当前尾部块已满 → 分配新块，将其指针追加到 map 尾部，O(1)（均摊）。

**头部 `push_front`**：
- 当前头部块仍有预留空位（头部块从中间或末尾开始填充，前面留白）→ 在前面构造元素，O(1)。
- 当前头部块头部已无空位 → 分配新块，将其指针插入 map 头部，O(1)（均摊）。

关键在于：头部块不从 `index 0` 开始存元素，而是从中间某处开始，前面预留空位，这样 `push_front` 可直接填充而无需移动。

### 随机访问 O(1)

给定全局下标 `i`，从 `deque` 的起始偏移 `start` 开始计算：

```
全局偏移 = start + i
块索引   = 全局偏移 / chunk_size
块内偏移 = 全局偏移 % chunk_size
element  = map[块索引][块内偏移]
```

两次数组寻址，O(1)，但比 `vector` 多一次间接跳转。

### 迭代器结构（4 指针）

GCC 的 `deque::iterator` 包含：
- `cur`：当前元素在块内的指针。
- `first`：当前块的起始地址。
- `last`：当前块的结束地址（one-past-end）。
- `node`：指向 map 中本块指针位置。

`++it` 时：`++cur`；若 `cur == last`，则跳到下一块（`++node`，重置 `first/last/cur`）。迭代器的自增操作比 `vector` 的 `++ptr` 复杂约 4~5 倍。

### 与 vector 的权衡

| 维度 | `deque` | `vector` |
|------|---------|---------|
| 头部插入/删除 | O(1) 均摊 | O(n) |
| 尾部插入 | O(1) 均摊 | O(1) 均摊 |
| 随机访问 | O(1)，多一次间接 | O(1)，直接寻址 |
| 缓存局部性 | 块内连续，跨块差 | 完全连续，最优 |
| 迭代器复杂度 | 高（4 指针）| 低（1 指针） |
| 内存开销 | 有 map + 块碎片 | 最小 |

`deque` 适合**需要两端高频插入/删除**的场景（如 BFS 队列），不适合随机访问密集型场景。
